# Legal documents — owner checklist

Two drafts live in this folder:

- [`terms-of-service-DRAFT.md`](./terms-of-service-DRAFT.md)
- [`privacy-policy-DRAFT.md`](./privacy-policy-DRAFT.md)

Both were written by auditing the codebase — the Supabase migrations, the Python backend, and
the React Native client — so they describe what the app **actually does**, not what a template
assumes. Both are **drafts** and **neither has been reviewed by a lawyer**.

They supersede `docs/archive/privacy-policy.md` (June 2026), which predates the entire social
layer, the moderation pipeline, "Who's That Pokémon", and RevenueCat, and is now materially
incomplete and in one place inaccurate (it claims deletion removes your scan data; it does
not — see §3 below).

---

## 1. Blockers — the app cannot ship as-is

### 1.1 The Terms and Privacy links in the app are dead text

`apps/spotlight-rn/src/features/auth/components/auth-controls.tsx:241-252` renders
"By signing up, you confirm to have read and agree to our **Terms of Use** and **Privacy
Policy**". The code comment says it plainly:

> `no hosted terms pages exist yet, so they are not tappable.`

The links are styled but not tappable, and there is no privacy policy URL anywhere in the app
or the backend. Apple requires a functional EULA link and a functional privacy policy link.
**Host both documents, then wire the links up.**

### 1.2 App Store Connect fields

- **Privacy Policy URL** (App Store Connect → App Privacy) — required.
- **EULA / Licence Agreement** — either accept Apple's standard EULA or paste a custom one.
  If you use the custom Terms here, paste them into App Store Connect → App Information →
  Licence Agreement.
- **Support URL** — required.
- Google Play requires the same privacy policy URL. `docs/android-play-store-submission-2026-07-20.md`
  already has "Privacy policy URL (host on Framer)" as an open checkbox.

### 1.3 Hosting

Both documents need real, stable, publicly reachable HTTPS URLs that do not require sign-in.
The `ekalight.com` domain is already in use for `api.ekalight.com` and `no-reply@ekalight.com`,
so `ekalight.com/terms` and `ekalight.com/privacy` are the natural homes. Convert the Markdown
to pages on whatever hosts the marketing site.

### 1.4 The generated iOS privacy manifest is wrong

`apps/spotlight-rn/ios/Ekalight/PrivacyInfo.xcprivacy` has `NSPrivacyTracking: false` (correct
— no IDFA, no ATT) but an **empty `NSPrivacyCollectedDataTypes` array**. That is inaccurate
given PostHog analytics, session replay, crash reporting, and everything the backend stores.
Note the `ios/` directory is gitignored and regenerated by prebuild, so fix this via the Expo
config, not by hand.

## 3. `[VERIFY]` items — where the code may need to change, not the document

These are places where the honest description of current behaviour is awkward. In most cases
the right fix is to **change the code and then make the cleaner claim**, rather than to publish
the awkward disclosure.

### 3.1 Deletion does not delete the images — highest priority

`backend/server.py:6415` `_ACCOUNT_DELETION_TABLES` deletes ten SQLite tables and then
best-effort deletes the Supabase auth user. It performs **zero cloud-storage calls**. So:

- Scan photographs, transaction photos, and labelling captures stay in the private bucket.
- Avatar and cover images stay in the public bucket, at `avatars/<user-uuid>.jpg` and
  `covers/<user-uuid>.jpg` — still publicly fetchable by anyone who knows the URL.

`backend/avatar_store.py:85` already defines `owner_object_paths(user_id)` — "Every object
`user_id` can own in the avatars bucket" — but **nothing calls it**. The helper for the fix
exists and is unwired.

The archived June policy claims deletion "permanently deletes your account, your collection,
and your scan data". That claim is **not currently true** of the images. Either wire up storage
deletion, or publish the honest disclosure now in Privacy §9.

### 3.2 Deletion misses several tables that hold user data

Not in `_ACCOUNT_DELETION_TABLES`, but keyed by user:

| Table | Holds |
|---|---|
| `user_emails` | **The user's email address** |
| `access_grants` | user_id + **email** |
| `access_waitlist` | **email** + user_id |
| `collections` | The user's named collections |
| `card_likes` | Public like signals |
| `labeling_sessions` | `labeler_user_id` |
| `scan_labeling_reviews` | `reviewer_user_id`; also not FK'd to `scan_events`, so it survives the scan's deletion |

Retaining a deleted user's **email address** is the one that matters most for a deletion-rights
claim. Recommend adding at least `user_emails`, `access_grants`, `access_waitlist`,
`collections`, and `card_likes` to the deletion list.

### 3.3 Scan images are retained forever

`tools/gcs-scan-artifacts-lifecycle.json` contains exactly one rule, and it is **not** a
deletion rule:

```json
{"rule":[{"action":{"type":"SetStorageClass","storageClass":"COLDLINE"},
          "condition":{"age":60,"matchesStorageClass":["STANDARD"]}}]}
```

Standard → Coldline at 60 days. Nothing is ever deleted. This is deliberate (the images are
training data), and the drafts say so honestly — but **decide whether you want an outer
retention bound**, and note there is currently **no user-facing opt-out** for having your scans
used to train the models. Artifact upload is automatic and fire-and-forget on every scan.

### 3.4 Humans can view other users' scan photos

`GET /api/v1/review/image/{scan_id}` (`backend/server.py:17686`), gated by
`_require_reviewer()`, serves scan photographs to an env-configured allowlist
(`SPOTLIGHT_REVIEWER_USER_IDS` / `SPOTLIGHT_REVIEWER_EMAILS`) so they can label scans —
including scans taken by other users. This is disclosed in Privacy §3.4. It is a legitimate
labelling workflow, but it must be disclosed, and it should stay allowlisted.

### 3.5 Deleted comment text is archived with no purge job

`social_17` moves the body of a soft-deleted comment into `deleted_content_bodies` (readable
only by the backend service role) so replies underneath it stay intelligible. The migration
flags the gap itself: *"Rows accumulate. There is no retention job yet. Right-to-erasure and
storage reclamation both become a scheduled service_role job... That job is future work."*
Build the purge job, or accept and disclose indefinite retention.

### 3.6 The staging bucket holds production scans

`backend/.env.production:70` sets `SPOTLIGHT_SCAN_ARTIFACTS_GCS_BUCKET=looty-staging`.
Production and staging user scans appear to be commingled in one bucket, while `looty-prod`
exists and is empty. Not a document problem, but it undercuts any statement about environment
separation and is worth fixing before launch.

### 3.7 Session token can fall back to plaintext storage

`apps/spotlight-rn/src/lib/supabase.ts` has a documented three-tier fallback: if the device
keychain fails, the Supabase session token is written **in plaintext to ordinary app storage**
under `@spotlight/auth/secure-store-fallback/…`. Consider failing closed instead. Flagged in
Privacy §12.

### 3.8 Unauthenticated account-existence oracle

`public.email_exists(text)` is `SECURITY DEFINER`, reads `auth.users.email`, and has EXECUTE
granted to `anon`. Anyone with the bundled anon key can test whether an email address has an
Ekalight account. The migration documents this as a deliberate product trade-off. Confirm you
want to keep it; the disclosure is in Privacy §6.

### 3.9 EXIF stripping is incidental, not deliberate

Uploads are re-encoded through `expo-image-manipulator`, which drops the original EXIF block
including GPS — but there is no explicit `exif: false` and no deliberate strip step, and **both
the profile and post upload screens fall back to uploading the raw picked file unchanged** if
the manipulator module fails to load (`edit-profile-screen.tsx:235`, `new-post-screen.tsx:172`).
In that fallback, original EXIF including GPS coordinates would be uploaded. Make the strip
explicit and make the fallback fail closed.

### 3.10 Unused microphone permission

`app.json` declares `NSMicrophoneUsageDescription` ("Allow Ekalight to access your
microphone."), inherited from the camera library. The app has no audio feature. Remove it, or
expect App Review to ask.

### 3.11 Account deletion reports success even when it partly fails

`_delete_supabase_auth_user` returns `False` and logs an ERROR if the service-role key is
missing or the admin call fails, but `delete_account` still returns `{"deleted": true}`. The
docstring explains the reasoning, and it is defensible — but confirm the ERROR is actually
alarmed on, since a silently misconfigured deploy leaves live auth users behind and re-triggers
a Guideline 5.1.1(v) rejection.

### 3.12 Anthropic and OpenAI retention

Confirm the data-processing terms and input-retention periods for both, and whether your
accounts are enrolled in zero-retention. The drafts currently leave this as `[VERIFY]`. This is
the answer to "what happens to my selfie after you send it to Anthropic".

## 4. Legal questions for counsel

### 4.1 CSAM
The app now has public image uploads. `backend/social_moderation_worker.py:52-55` says it
directly: `omni-moderation` "is NOT sufficient for child-sexual-abuse material. Before public
image uploads scale, add hash-matching (PhotoDNA / Cloudflare CSAM tool) + the legally-required
NCMEC reporting path." US providers have mandatory NCMEC reporting duties under 18 U.S.C.
§ 2258A on actual knowledge. **Get advice before launch, not after.**

### 4.2 Minors
No age gate, no date of birth, no parental-consent flow, and guest mode requires nothing at
all. Combined with public profiles, public image posting, and user-to-user DMs, this attracts
COPPA, the UK Age Appropriate Design Code, and a growing set of US state minor-safety laws.
Decide: age gate at sign-up, minimum-age attestation, DM restrictions for minors, and the
App Store age rating.

### 4.3 EU/UK
If you have EU/UK users: analytics and **session replay** commonly require consent rather than
legitimate interests, which would mean a consent prompt the app does not currently have. Also
Article 27 representative, transfer mechanism, and — if you grow — DSA notice-and-action,
statement-of-reasons, and appeal obligations. The moderation section is written to be
DSA-friendly but is not a compliance programme.

### 4.4 Subscriptions
> **Update 2026-08-12:** RevenueCat (SDK, staging key, and the paywall UI) was removed from the
> app entirely pending a future monetization pass — the paragraphs below describe the pre-removal
> state and remain as reference for when subscriptions are revisited.

The paywall UI and RevenueCat are wired, but `EXPO_PUBLIC_REVENUECAT_IOS_KEY` is set only in
the **staging** EAS profile. In production there is no key, so `requestPremiumUnlock()` returns
`'interim'` and grants a **free local unlock**. So today there is no live subscription and no
purchase data. Two consequences:

- ToS §13 can be deleted if you launch without purchases. If you launch with them, Apple's
  Guideline 3.1.2 requires specific auto-renewable subscription disclosures in the EULA.
- RevenueCat is configured **without** an app user ID and with no `logIn()` call, so
  entitlements are device-scoped, not account-scoped. If you go live, that is a product bug as
  well as a privacy statement to correct — a user who reinstalls loses their subscription.

## 5. App Store Connect privacy questionnaire

Based on the audit, here is what the App Privacy questionnaire should reflect. **Check each
against the final shipped build.**

| Data type | Collected? | Linked to identity? | Used for tracking? | Purpose |
|---|---|---|---|---|
| Email address | **Yes** | Yes | No | App functionality |
| Name (display name) | **Yes** | Yes | No | App functionality; **also sent to PostHog** as the person `name` property |
| User ID | **Yes** | Yes | No | App functionality, analytics |
| Photos (card scans, post images, avatars, transaction photos) | **Yes** | Yes | No | App functionality, analytics/product improvement (**model training**) |
| Photos ("Who's That Pokémon" selfie) | **Transmitted and processed, not retained** | No | No | App functionality |
| User content (posts, comments, DMs) | **Yes** | Yes | No | App functionality |
| Other user content (bio, location text, link) | **Yes** | Yes | No | App functionality |
| Purchase history | **Not currently** | — | — | Revisit if RevenueCat goes live |
| **Financial info** (cost basis, sale prices, profit) | **Yes** | Yes | No | App functionality. Easy to overlook — the collection tracks real money |
| Product interaction / usage data | **Yes** | Yes | No | Analytics |
| Crash data | **Yes** | Yes | No | App functionality |
| Performance data | **Yes** | Yes | No | Analytics |
| Device ID / advertising ID | **No** | — | — | No IDFA, no ATT, no cross-app tracking |
| Precise or coarse location | **No** | — | — | The profile "location" is free text the user types, not device location |
| Contacts, health, browsing history | **No** | — | — | |

Answer **"No"** to tracking across apps and websites — that is accurate and is a genuine
selling point.

Note the two answers most likely to be got wrong by someone filling this in from memory:
**financial info is collected** (cost basis and sale prices), and **the display name is sent to
a third-party analytics provider** (the email is not).

## 6. Things the audit found that a template would have got wrong

Kept here because they are the reason these drafts differ from a generic policy.

1. **PostHog does receive the display name.** Email is deliberately excluded and the code says
   so, but `name` is sent as the canonical person property. "No PII to analytics" would have
   been false.
2. **Session replay is enabled**, with images and text inputs masked. A template would not have
   mentioned it at all.
3. **The selfie is not stored but is transmitted to Anthropic.** Both halves matter. The in-app
   caption "Analyzed in the moment. Never stored." is true about storage and silent about
   transmission.
4. **Post images live in a private GCS bucket, not Supabase Storage.** The migrations create a
   `post-media` Supabase bucket, but the running code migrated off it. The design doc is stale
   on this point.
5. **Avatars and covers are in a public bucket** at a URL containing the user's auth UUID —
   world-readable without sign-in.
6. **Posts are public to everyone, not followers-only**, and because guests are technically
   authenticated, "signed-in users" means "anyone who installs the app".
7. **DMs are not sent to the AI moderation pass** — only the wordlist prefilter. Claiming full
   DM moderation would have been an overclaim.
8. **No push notifications exist**, so no device tokens are stored. Templates always include
   them.
9. **No IP logging server-side** — `log_message` is explicitly suppressed.
10. **Deletion does not delete images or the user's email.** See §3.1 and §3.2.
11. **Scan images are retained forever by design** and are used for training, with no opt-out.
12. **Card scan data is financial data** in the questionnaire sense, via cost basis and sales.
